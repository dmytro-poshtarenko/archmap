# Посібник із розмітки еталона

Версія: 1.1

- **Комплекс:** Rocket.Chat. Знімки репозиторіїв зафіксовано в `configs/rocketchat.lock.json`.
- **Профіль розгортання:** мікросервіси. Змінна `TRANSPORTER` вказує на NATS, тож окремі сервіси працюють у власних контейнерах.
- **Описи інфраструктури:** `docker-compose-ci.yml` основного репозиторію та Helm-чарт `rocketchat`.

Цей посібник — письмовий протокол розмітки. Його фіксують у git до початку розмітки, і кожна мітка зберігає версію посібника, за якою її зроблено. Якщо після пілотної розмітки посібник зміниться, він отримає нову версію (розділ 10).

## 1. Що розмічаємо

Еталон потрібен, щоб виміряти повноту й точність карти міжсервісних зв'язків. Для кожного рядка вибірки розмітник відповідає на три запитання:

1. Чи є в цьому рядку місце виклику?
2. Якщо є, то яка його ціль у комплексі, або цілі немає?
3. До якого з восьми випадків належить зв'язок?

Мовну модель до розмітки не залучаємо. Відповідей засобу розмітник не бачить: інтерфейс розмітки їх не читає й не показує.

**Міжсервісний зв'язок** — взаємодія двох окремо розгорнутих частин комплексу. Виклики всередині однієї розгорнутої частини зв'язками не є.

**Місце виклику** — найзовнішній виклик у коді застосунку, з якого можна вивести адресу або назву цілі (розділ 3).

## 3. Місце виклику

### 3.1 Що вважаємо місцем виклику

| Тип | Місце виклику | Приклади форм у Rocket.Chat |
|---|---|---|
| `http` | Запит HTTP через клієнт або його обгортку | `useEndpoint('GET', '/v1/rooms.info')`, `sdk.rest.post(…)`, `fetch(url)`, `Livechat.deleteVisitor()` |
| `ddp` | Виклик методу Meteor або підписка через вебсокет | `useMethod('saveSettings')`, `sdk.call(…)`, `Meteor.call(…)`, `useStream('notify-room')`, `sdk.stream(…)` |
| `broker` | Виклик дії сервісу Moleculer, публікація події або підписка на неї | `Presence.setStatus(…)`, `api.call('presence.x', …)`, `api.broadcast('user.nameChanged', …)`, `api.emitToOne(…)`, `api.broadcastToServices([…], 'подія', …)`, `this.onEvent('watch.users', …)` |
| `db` | Звернення до колекції MongoDB | `Users.findOneById(uid)`, `Rooms.updateOne(…)`, `db.collection(…)` |
| `trigger` | Оголошення фонової задачі за розкладом | `cronJobs.add('NPS', …)` |

Таймери в межах процесу (`setInterval`, `setTimeout`) тригерами не є: задачу запускає той самий процес.

### 3.2 Найзовнішній виклик

Обгортка, яка отримує адресу параметром, — не місце виклику. Місцем виклику є виклик цієї обгортки з конкретною адресою, а внутрішній виклик позначаємо як «не місце виклику» з причиною `wrapper-internal`:

```ts
function callServer(method: string, ...args: unknown[]) {
  return sdk.client.callAsync(method, ...args); // wrapper-internal
}

callServer('livechat:sendMessage', message); // місце виклику
```

Обгортка, яка задає адресу сама, — навпаки. Наприклад, у `function getRoomInfo(rid) { return sdk.rest.get('/v1/rooms.info', { roomId: rid }); }` місцем виклику є внутрішній `sdk.rest.get`, а виклики `getRoomInfo(…)` окремими місцями не є.

Методи клієнтських бібліотек, що відповідають окремим маршрутам, — місця виклику; їхні внутрішні запити позначаємо `wrapper-internal`. Приклад — `Livechat.deleteVisitor()` з `@rocket.chat/ddp-client`.

Фабрика, яка фіксує адресу й повертає функцію (`useEndpoint`, `useMethod`, `useStream`), сама є місцем виклику. Подальші виклики повернутої функції окремими місцями не є.

### 3.3 Багаторядковий виклик

Один виклик — одне місце. Інтерфейс позначає ● інші рядки-кандидати поблизу.

- Якщо той самий виклик має рядок-кандидат вище, позначте поточний рядок як `duplicate`.
- Інакше розмітьте виклик на поточному рядку й клацніть із Shift номер його останнього рядка.

### 3.4 Коли рядок — не місце виклику

| Причина | Коли |
|---|---|
| `not-a-call` | Імпорт, коментар, тип, рядкова константа, побудова адреси без запиту (`info: \`${serverUrl}api/info\``) |
| `declaration` | Оголошення обробника, а не виклик: `API.v1.get('rooms.info', …)`, `router.get('/x', handler)`, `Meteor.methods({…})` |
| `duplicate` | Рядок виклику, який уже має кандидата вище (3.3) |
| `wrapper-internal` | Внутрішній виклик обгортки чи бібліотеки, адреса надходить параметром (3.2) |
| `other` | Інше; поясніть у примітці |

## 4. Тип взаємодії

Тип відповідає способам взаємодії з табл. 2.1 плану роботи. HTTP і DDP — це «запит через мережу», брокер — «черга повідомлень», БД — «спільна база даних», тригер — «запуск за подією».

| Тип | Вид ключа цілі |
|---|---|
| `http` | `http` |
| `ddp` | `ddp` |
| `broker` | `action` для дій, `event` для подій |
| `db` | `coll` |
| `trigger` | `timer` |

Інтерфейс пропонує тип за шаблоном, який знайшов рядок. Якщо він хибний, змініть його.

## 5. Ціль

### 5.1 Ключ цілі

Ключ має вигляд `вид:метод:назва@компонент`.

| Ціль | Ключ | Приклад |
|---|---|---|
| Маршрут HTTP | `http:<МЕТОД>:<шаблон маршруту>@<компонент>` | `http:GET:/api/v1/rooms.info@rocketchat` |
| Метод Meteor | `ddp:call:<назва>@<компонент>` | `ddp:call:saveSettings@rocketchat` |
| Підписка, потік | `ddp:sub:<назва>@<компонент>` | `ddp:sub:notify-room@ddp-streamer-service` |
| Дія брокера | `action:-:<сервіс>.<дія>@<компонент>` | `action:-:presence.setStatus@presence-service` |
| Подія брокера | `event:-:<назва>@*` | `event:-:user.nameChanged@*` |
| Колекція MongoDB | `coll:-:<колекція>@mongo` | `coll:-:rocketchat_room@mongo` |
| Задача за розкладом | `timer:-:<назва>@<компонент>` | `timer:-:NPS@rocketchat` |
| Цілі в комплексі немає | `NONE` і причина (5.4) | — |

**HTTP.**
- Шаблон маршруту записуйте так, як його оголошено в обробнику, з префіксом `/api`: клієнтський шлях `/v1/x` — це `/api/v1/x`.
- Параметри шляху — у формі оголошення: `/api/v1/livechat/visitor/:token`. Назви параметрів значення не мають: ключі порівнюються так, ніби всі параметри названо однаково, тож `:uid` і `:agentId` в одній позиції рівнозначні.
- Метод HTTP — великими літерами.

**DDP.** Назва методу чи потоку — так, як її передають у виклику: `notify-room`, а не `stream-notify-room`.

**Брокер.**
- `<сервіс>` — простір імен сервісу Moleculer (`presence`, `license`, `authorization`), а не ім'я проксі (`Presence`).
- `<дія>` — назва методу.

**Подія.** Компонент завжди `*`, бо подію доставляють усім підписникам.

**Колекція.** Пишіть справжню назву колекції MongoDB з префіксом `rocketchat_`; виняток — `users`. Каталог показує, якій моделі відповідає колекція, наприклад «Rooms (RoomsRaw)».

**Компонент цілі.** Це частина, чий код обробляє звернення, тобто оголошення маршруту, методу, дії чи задачі. Проміжні ланки до ключа не входять, як-от шлюз `traefik` або `ddp-streamer-service`, що пересилає метод на сервер. Якщо ж проміжна ланка обробляє звернення сама, ціль — вона. Так ddp-streamer сам обробляє методи входу та присутності (5.2).

**Каталог.** Поле цілі підказує ключі з каталогу, зібраного з типізованих оголошень Rocket.Chat: rest-typings, `ServerMethods`, інтерфейсів сервісів, сигнатур подій, моделей і задач. Каталог — лише підказка. Якщо потрібного ключа в ньому немає, перевірте ціль у коді, впишіть ключ і додайте його до каталогу кнопкою.

### 5.2 Куди веде звернення в профілі мікросервісів

| Що викликають | Ціль |
|---|---|
| REST `/api/…` | `rocketchat` |
| Метод Meteor | `rocketchat`: ddp-streamer приймає вебсокет і пересилає метод на сервер через брокер |
| Методи `login`, `logout`, `setUserStatus`, `UserPresence:online`, `UserPresence:away`, `UserPresence:setDefaultStatus` | `ddp-streamer-service`: обробляє їх сам |
| Потік (`useStream`, `sdk.stream`) | `ddp-streamer-service` |
| Дії сервісу `presence` | `presence-service` |
| Дії сервісів `authorization`, `abac` | `authorization-service` |
| Дії сервісу `accounts` | `account-service` |
| Дії сервісу `queue-worker` | `queue-worker-service` |
| Дії сервісу `omnichannel-transcript` | `omnichannel-transcript-service` |
| Дії будь-якого іншого сервісу брокера | `rocketchat` |
| Колекція MongoDB | `mongo` |
| Задача `cronJobs` | Компонент, у якому працює код, що її реєструє |

Звідки ці дані:
- `apps/meteor/server/services/startup.ts` і `apps/meteor/ee/server/startup/services.ts` — які сервіси сервер не реєструє, коли `isRunningMs()`;
- `ee/apps/*/src/service.ts` — які сервіси реєструє кожен контейнер;
- `ee/apps/ddp-streamer/src/methods/*.ts` — методи, які ddp-streamer обробляє сам;
- мітки traefik у `docker-compose-ci.yml`.

### 5.3 Де працює код спільних пакетів

| Пакет | Де працює в профілі мікросервісів |
|---|---|
| `ee/packages/presence` | `presence-service` |
| `packages/authorization`, `ee/packages/abac` | `authorization-service` |
| `ee/packages/omnichannel-services` | `omnichannel-transcript-service`, `queue-worker-service` |
| `packages/ui-*`, `packages/fuselage-*`, інші пакети інтерфейсу | Клієнти, які їх імпортують |
| Інші серверні пакети (`packages/models`, `packages/core-services` тощо) | `rocketchat` і всі мікросервіси, що їх імпортують |

Якщо код пакета працює в кількох частинах, вважайте, що виклик виконується в кожній із них. Ціль розмічайте, якщо хоча б з однієї з цих частин виклик веде в іншу частину. Наприклад, `License.hasModule()` у `ee/packages/presence` виконується в `presence-service`, а сервіс `license` працює в `rocketchat`. Отже, ціль — `action:-:license.hasModule@rocketchat`.

### 5.4 Коли цілі немає

Причину вибирайте з таких:
- **`external`** — зовнішня система: Rocket.Chat Cloud, OAuth-провайдери, вебхуки, сервери Matrix, LiveKit, SMTP тощо.
- **`intra`** — ціль працює в тій самій розгорнутій частині, що й код виклику. Наприклад, сервер викликає дію сервісу брокера, що теж працює в `rocketchat` (`Team.create(…)`, `Message.saveMessage(…)`). Або серверний код викликає власний метод Meteor через `Meteor.callAsync`. Сюди ж належить `api.broadcastLocal(…)`: подію отримує лише той самий процес.
- **`client-local`** — локальні сховища й об'єкти клієнта з іменами моделей чи сервісів: `Messages.use(…)`, `Rooms.use(…)`, клієнтський `Presence`.
- **`other`** — інше; поясніть у примітці.

## 6. Номер випадку

Випадок визначає, яких відомостей **потрібно**, щоб однозначно знайти ціль. Він не залежить від того, які механізми трапляються на шляху запиту. Наприклад, усі запити REST проходять через `traefik`, але шлях `/api/v1/…` має лише `rocketchat`, тож правило шлюзу для них не потрібне.

Перевіряйте випадки від 8 до 1. Перший, що підходить, і є номером зв'язку: якщо підходить кілька, зараховується більший.

| № | Випадок | Ознака | Приклади в Rocket.Chat |
|---|---|---|---|
| 8 | Ціль стає відомою лише під час роботи | Адреса чи назва надходить із бази даних, від користувача або від застосунку Apps-Engine, і ні код, ні описи інфраструктури її не визначають | Назва методу, прочитана з повідомлення чи налаштувань застосунку |
| 7 | Ціль визначає правило шлюзу | Звернення можуть обробити дві частини, і лише правило traefik вибирає одну | Методи входу й присутності, потоки: `/websocket` веде до `ddp-streamer-service` |
| 6 | Однакова ціль у кількох частинах, інфраструктура не розрізняє | Після аналізу коду й описів інфраструктури лишається ≥ 2 частини; ціль видно лише з контексту: назв, коментарів, документації | Однаковий шлях у двох сервісах без правила шлюзу |
| 5 | Ціль оголошено механізмом без правил | Обробник оголошено механізмом, для якого в зафіксованому наборі немає правил (див. нижче) | `useMethod('saveSettings')` → метод `Meteor.methods` |
| 4 | Розміщення задано в налаштуваннях | Щоб вибрати частину-ціль, потрібне значення змінної середовища чи налаштування | Дії сервісів `presence`, `authorization`, `abac`, `queue-worker`, `omnichannel-transcript`: їхній контейнер залежить від `TRANSPORTER` |
| 3 | Адресу приховано за допоміжною функцією | Адресу чи назву видно лише після переходу до оголошень: обгортки, константи, проксі, методу бібліотеки | Проксі `Presence` → `proxify('presence')`; модель `Users` → `UsersRaw` → `super(db, 'users')`; `Livechat.deleteVisitor()`; конструктори URL десктопного клієнта; назва задачі в константі |
| 2 | Адреса з підстановками, шлях видно повністю | Є підстановки, але шаблон шляху чи назви визначено | `` sdk.rest.get(`/v1/livechat/agents/${userId}/departments`, …) `` |
| 1 | Адресу записано безпосередньо | Адресу чи назву записано в місці виклику | `useEndpoint('GET', '/v1/rooms.info')`, `api.broadcast('user.nameChanged', …)`, `cronJobs.add('NPS', …)` |

**Зафіксований набір правил**, від якого залежить випадок 5:
- **Правила є** для REST-маршрутизатора Rocket.Chat (`API.v1.*`), Express, брокера Moleculer (сервіси, дії, події), моделей MongoDB (`registerModel`, `BaseRaw`) і задач `cronJobs`.
- **Правил немає** для методів і публікацій Meteor (`Meteor.methods`, `Meteor.publish`), потоків `Streamer` і власного DDP-сервера ddp-streamer (`server.methods`).

Сталі базові шляхи відомих клієнтів, як-от `/api` для `useEndpoint` і `sdk.rest`, належать до самого клієнта й адресу не приховують.

Номер випадку ставимо лише тоді, коли в місця виклику є ціль.

### 6.1 Типові форми Rocket.Chat

| Форма | Ціль | Випадок |
|---|---|---|
| `useEndpoint('GET', '/v1/rooms.info')` | `http:GET:/api/v1/rooms.info@rocketchat` | 1 |
| `` sdk.rest.get(`/v1/livechat/agents/${id}/departments`) `` | `http:GET:/api/v1/livechat/agents/:agentId/departments@rocketchat` | 2 |
| `Livechat.deleteVisitor()` | `http:DELETE:/api/v1/livechat/visitor/:token@rocketchat` | 3 |
| `useMethod('saveSettings')` | `ddp:call:saveSettings@rocketchat` | 5 |
| `Meteor.call('UserPresence:away')` у десктопному клієнті | `ddp:call:UserPresence:away@ddp-streamer-service` | 7 |
| `useStream('notify-room')` | `ddp:sub:notify-room@ddp-streamer-service` | 7 |
| `Presence.setStatus(…)` із сервера | `action:-:presence.setStatus@presence-service` | 4 |
| `License.hasModule(…)` у `presence-service` | `action:-:license.hasModule@rocketchat` | 3 |
| `Team.create(…)` із сервера | `NONE` (`intra`) | — |
| `api.broadcast('user.nameChanged', …)` | `event:-:user.nameChanged@*` | 1 |
| `Users.findOneById(uid)` | `coll:-:users@mongo` | 3 |
| `Messages.use(…)` у вебклієнті | `NONE` (`client-local`) | — |
| `cronJobs.add('NPS', …)` | `timer:-:NPS@rocketchat` | 1 |
| `serverFetch('https://cloud.rocket.chat/…')` | `NONE` (`external`) | — |

Назви параметрів шляху (`:agentId`) беріть з оголошення маршруту; каталог показує їх у ключі.

## 7. Перевірка пропусків

Текстовий пошук може пропустити місця виклику. Щоб оцінити, скільки саме, 20 випадково обраних файлів, які імпортують HTTP-клієнт або клієнт брокера, читаємо повністю. Вкладка «Перевірка пропусків» показує файл без позначок кандидатів, тож рядки, які знайшов пошук, не виділено. Порядок дій:

1. Прочитайте файл від першого до останнього рядка.
2. Для кожного місця виклику клацніть номер його першого рядка. Для багаторядкового виклику клацніть із Shift номер останнього рядка.
3. Розмітьте місце виклику так само, як у вибірці.
4. Позначте файл як прочитаний повністю.

## 8. Другий розмітник

Другий розмітник — інша особа з досвідом розробки — незалежно розмічає випадкові 20 % вибірки в кожній страті.

1. Він запускає інтерфейс командою `archmap label serve --annotator B --second` і бачить лише свої місця. Мітки першого розмітника йому не показуються.
2. До завершення розмітки обидва розмітники не обговорюють окремих місць.
3. Після завершення команда `archmap label agreement --split dev` обчислює каппу Коена окремо для цілі й для випадку.
4. Розбіжності обговорюють. Узгоджену мітку записує перший розмітник, а початкові мітки обох лишаються для обчислення каппи.

## 9. Порядок роботи

1. **Пілот.** Розмітьте перші 30 місць частини dev — по 6 кожного типу. Запишіть, які правила посібника виявилися неоднозначними.
2. **Уточнення.** Якщо посібник змінився, підніміть його версію (розділ 10) і перегляньте мітки пілоту.
3. **Основна розмітка.** Спершу розмітьте частину dev, потім test.
4. **Перевірка пропусків** — 20 файлів (розділ 7).
5. **Другий розмітник** — розділ 8.

Мітки тестової частини до фіксації методу не експортуються й не аналізуються: інструмент відмовляє в такому доступі.
